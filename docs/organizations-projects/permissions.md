# Разрешения организаций и проектов

## Коды

В каталоге уже были `organizations.create`, `projects.read` (`g-projects`) и `projects.create`. Добавлены только недостающие строки:

| Код | Grant id | Область проверки |
| --- | --- | --- |
| `organizations.read` | `g-organizations-read` | организация или покрывающая её корпоративная область |
| `organizations.create` | `g-organizations-create` | корпорация установки, в которой создаётся организация |
| `organizations.update` | `g-organizations-update` | организация или покрывающая её корпоративная область |
| `projects.read` | `g-projects` | проект, его организация или покрывающая корпоративная область |
| `projects.create` | `g-projects-create` | организация, в которой создаётся проект |
| `projects.update` | `g-projects-update` | проект, его организация или покрывающая корпоративная область |

`organizations.manage` (`g-org-manage`) не используется как синоним read, create или update. `ACTION_COVERS` эти действия друг из друга не выводит.

Создание организации не проверяется по ещё не существующему `organizationId`. Создание проекта не проверяется по будущему `projectId`.

Read не даёт update. Update не даёт create и не даёт read. Кнопка изменения на экране показывается, когда объект уже прочитан и в ответе справочника `can_update`. Сервис всё равно проверяет само действие `update`, а не видимость кнопки.

## Кто получает коды

Capability `corporate_superadmin` по-прежнему разворачивается в известный каталог на корпорации установки. Неизвестный resource или action владельцу не разрешается. `can()` для владельца не заменён на безусловный `true`.

Миграция схемы 9 дописывает новые строки только в каталог grants. Списки `grantIds` сохранённых ролей не меняются. Новые коды выдаются через существующий редактор ролей. Одинаковое отображаемое имя роли capability не даёт. Поле `user.role` не используется.

`canDelegate`, пределы делегирования, запрет самоповышения и расширения области не менялись. Право выполнить действие не равно праву передать его.

Навигация смотрит `effectiveGrants` и `systemCapabilities`. Делегирование в этот список не входит и экран не открывает. Область `own` и `tasks.read` экран не открывают. Название роли не проверяется.

Пункт виден суперадминистратору и пользователю, у которого хотя бы одно из шести разрешений есть на области `project`, `organization` или `corporation`. Sidebar и карточки главной берут один реестр.

## Что не ослаблено

Формы и разделы остаются организационными: без проекта они доступны, если есть соответствующее чтение. Задачи остаются проектными: без выбранного проекта раздел задач — `needs-context`. «Создать задачу» без положительного `projectId` не вызывает создание и показывает, что сначала нужен проект.
