# Первичная установка на моках

Документ описывает локальную модель этого этапа. Это не контракт production-сервера и не интеграция с 1С или корпоративным входом.

## Два сценария

Выбор хранится в `inlog:mock:scenario` и не входит ни в одну базу.

| Сценарий | База IndexedDB | Начальное состояние |
| --- | --- | --- |
| Демонстрация | `inlog:mock:corporate-v2` | Прежний `createSeed()` |
| Моя тестовая установка | `inlog:mock:personal-v1` | Пустая установка |

Демонстрация остаётся сценарием по умолчанию. Открытие страницы не копирует её в личную установку и не засеивает личную установку повторно, если та уже настроена.

Документ запоминает сценарий при первом чтении. Запись другого сценария в storage не переключает уже открытую вкладку. Смена сценария завершает сессию, отпускает writer lock этого документа и перезагружает страницу.

Изоляция охватывает базу, ключи сессии, черновики `inlog:session-draft:` / `inlog:mock:personal:draft:` и доску. Ключ доски включает namespace. Одинаковый числовой `userId` в двух базах — разные люди; старые доски и черновики не переносятся.

Сброс «Начать мою установку заново» вызывает `resetMockNamespace` только для `inlog:mock:personal-v1`. Он не вызывает `localStorage.clear()` и не удаляет базы IndexedDB. Отказ writer lock не меняет запись и не считается успехом.

## Корпорация установки

`installationCorporationId` — явная идентичность корпорации, записанная серверной операцией настройки. Клиентский payload её не задаёт.

Пока организаций и проектов нет, проверка области принимает корпоративную область только если она совпадает с этим идентификатором. Если организации уже есть и расходятся с идентификатором, область не подтверждается. Старый снимок без поля по-прежнему выводит одну известную корпорацию из организаций и проектов.

Суперадминистратор получает известный каталог разрешений на эту корпорацию во время проверки. Списки разрешений сохранённых ролей при этом не дополняются. `organizations.read`, `organizations.create`, `organizations.update`, `projects.read`, `projects.create` и `projects.update` — отдельные разрешения каталога. Одно не следует из другого и не следует из `assignments.update` или `roles.update`.

## Первичная настройка

Мастер доступен только в mock, только когда установка не настроена: фаза `uninitialized`, нет пользователей, нет идентичности корпорации и нет `corporate_superadmin`. Проверка повторяется внутри записи.

Одна запись создаёт корпорацию с серверным id `1`, первого пользователя, локальный проверочный материал пароля и capability `corporate_superadmin`. Пользователь остаётся `legacyRole: member`: доступ не выдаётся через старое поле роли. Повторный запрос получает `already_configured` и не создаёт второго владельца. Ошибка до записи оставляет установку пустой.

Сохранение настройки и выдача сессии — две операции. Если вход после сохранения не удался, ответ `{ configured: true, signedIn: false }`. Повторно создавать владельца нельзя; дальше используется обычный `/login`.

Пароль владельца проверяется по соли и SHA-256 из Web Crypto. Открытый пароль не хранится и не попадает в справочник, `users/me` и dev-список. Общий fixture-пароль принимается только у демонстрационных пользователей с `fixturePassword: true` и без локального credential.

## Справочник

Симуляция хранит строки источника отдельно от пользователей. Ключ строки — идентификатор кадровой записи. `providerId` и `externalSubject` — отдельная явная связь корпоративного входа. Почта и имя никого не сопоставляют.

Синхронизация создаёт или обновляет профиль и допустимое членство организации. Повтор той же кадровой записи обновляет того же пользователя, в том числе после смены почты. Уже занятый `externalSubject` не перехватывается. Несвязанная тень с тем же subject получает `userId`, а не вторую идентичность.

Синхронизация не назначает роли и capability, не меняет assignments, delegation и ручные ограничения, не трогает локальный credential владельца и не удаляет отсутствующие в загрузке записи. Увольнение и приоритет блокировок в этот этап не входят.

Членство получает вид организации. Организация-заказчик не становится лабораторией.

## Доступ сотрудника

После синхронизации у сотрудника нет назначений. Вход через mock SSO без назначения оставляет существующий экран «Доступ пока не назначен». Назначение и отзыв идут через текущие роли, `createAssignment` / `revokeAssignment`, `expectedAccessVersion`, аудит и инвалидацию.

«Скопировать адрес входа» копирует адрес `/login` текущей установки. В адресе нет токена, пароля и роли. Письмо не отправляется.

Схема документа поднята до 9, потому что появились поля установки, credential и справочника. Миграция не очищает данные и не дописывает новые разрешения в сохранённые роли.
