## 2. Архитектура навигации

Реестр разделов живёт в `src/app/navigation/catalog.ts`. Это слой композиции приложения. Shared его не импортирует.

У раздела есть id, ключи подписи и короткого описания, маршрут, группа, требуемый контекст, поверхность и правило доступа. Sidebar и карточки главной берут один и тот же список `visibleNavigation` / `homeCards`. Быстрые действия считаются отдельно: `visibleQuickActions`.

Поверхности:

- `navigation` — sidebar и карточки: главная, задачи, конструктор, отчёты, профиль, уведомления.
- `nested` — шаблоны задач. Остаются внутри планировщика, в обычное меню не выносятся.
- `preserved` — прямой URL, в рабочую навигацию не входят.

Доступность считается по операционным grants (`resource` + `action` + scope project/organization/corporation). Название роли, каталог делегирования и `corporate_superadmin` в это правило не входят. Делегирование не открывает действие.

Состояния: `allowed`, `needs-context`, `denied-here`, `unavailable`, `not-enforced`. В меню остаются `allowed`, `needs-context` и `denied-here`: пункт не прячется только потому, что проект ещё не выбран или выбранный контекст чужой. `unavailable` скрывает раздел. Пока grants не пришли, рабочие разделы не показываются, чтобы не мигнуть.

Live (`enforceGrants: false`) не получает mock-grants. Реализованные разделы и три быстрых действия остаются доступными, сервер остаётся проверкой. Это не перевод live-навигации на новую модель.

Выбранные организация и проект по-прежнему только в URL (`org`, `project`). Второй источник не добавлялся. Ссылки строит `workspaceHref`. `task`, `node` и `tab` в другой раздел не копируются. Публичные ссылки и выход рабочие параметры не получают. Переключателя корпораций нет: в действующих контрактах его нет.

Оболочка: `src/app/shell/AppShell.tsx`. Слева sidebar (`md+`), сверху компактная шапка, контент справа. Ниже `md` sidebar открывается drawer; после выбора раздела drawer закрывается, фокус уходит на первый элемент, Escape закрывает. Шапка не сжимает заголовок раздела в обрывки: выбор организации и проекта переносится на следующую строку. Текущий пользователь подписан через `useGetMeQuery` внутри оболочки, иначе кэш `getMe` после bootstrap пропадал примерно через минуту и имя исчезало из приветствия и подвала.

Утверждённый макет главной как исходник вёрстки не использовался. Экран собран по визуальным требованиям этого этапа: светлый рабочий фон, белые поверхности, существующий акцент, тёмная тема через уже имеющийся переключатель.

## 3. Пункты меню и permissions

| Раздел | Маршрут | Что решает показ |
| --- | --- | --- |
| Главная | `/` | всегда |
| Задачи | `/scheduler/tasks` | `tasks.read` хотя бы в одном доступном scope. Без `projectId` пункт остаётся и ведёт к выбору. В чужом проекте пункт остаётся, страница сообщает об отсутствии права |
| Конструктор | `/admin/constructor` | `constructor.schema` `read` на организацию. `records.read` само по себе пункт не открывает. `schema.update` не даёт отчёты и записи |
| Отчёты | `/admin/reports` | `reports.read`. Кнопка построения на странице по-прежнему требует `reports.generate` |
| Профиль | `/settings/profile` | всегда |
| Уведомления | `/settings/notifications` | всегда; список остаётся в шапке, на главной не дублируется |

Быстрые действия:

- «Создать задачу» — есть и `tasks.read`, и `tasks.create`. Открывает существующий диалог задач через `sessionStorage` (`inlog:task-compose`), не через выдуманный URL-параметр. Если контекста нет, переход ведёт к выбору.
- «Открыть конструктор» — `constructor.schema` `read`.
- «Построить отчёт» — `reports.read` и `reports.generate`.

Если в выбранном контексте права нет, быстрое действие скрывается. Пункт меню при этом может остаться, чтобы сменить контекст.

Старая платформенная админка (`/admin/users` и соседние `/admin/*`) в новое меню не добавлена. `AdminRoute` по-прежнему смотрит на legacy-роль, а не на grants. Администратор лаборатории этот пункт не получает.

## 7. Writer lease после reload

Причина из отчёта 2А-3 подтверждена кодом и тестом. `writerId` жил только в памяти модуля как `tab-${crypto.randomUUID()}`. Обычный reload создаёт новый realm и новый id. Неистёкшая запись в IndexedDB с прежним id считалась чужой вкладкой (`ownerId !== writerId`), запись получала 409 `mock_writer_held`, чтение продолжало работать. Таймаут 60 секунд не сокращался и защита не отключалась.

Исправление: id вкладки хранится в `sessionStorage` под ключом `inlog:mock:writer-tab`. Reload той же вкладки читает тот же id. `setMockWriterId` для тестов ключ не переписывает. На `pagehide` lease не снимается, чтобы reload не устраивал гонку. Чужой живой lease не удаляется.

Доказательства:

- `src/app/mocks/db/repository.test.ts`: после «reload» тот же session id снова пишет; второй namespace с `ownerId` `tab-other-live` остаётся `writeLocked`, update и reset бросают `MockWriterHeldError`, владелец не подменяется.
- Браузер, одна вкладка, origin 5178: создание узла вернуло 201. Сразу после reload следующий POST на ту же коллекцию тоже вернул 201 (id 4), примерно через 30 мс после появления оболочки. Ожидания 60 секунд не было.

Ограничение: если браузер копирует `sessionStorage` в дубликат вкладки, обе получат один id. Это не кража lease у вкладки с другим id. Вторая живая вкладка в браузере отдельно не открывалась; отказ чужому владельцу покрыт unit-тестом.

## 12. Завершающая приёмка 2Б

Новых разделов и конструкторов нет. Рабочая mock-база и origin `5173` не открывались и не сбрасывались. Проверка в браузере шла на уже запущенном mock `http://127.0.0.1:5178`. Commit и push не делались.

### Writer

`sessionStorage` хранит только линию вкладки (`inlog:mock:writer-tab`). У каждого документа свой epoch, он живёт только в памяти. Право записи даёт исключительный lock (`navigator.locks`, в среде без этого API — замок внутри realm). Lease на 60 секунд не сокращался.

- Reload того же документа освобождает lock вместе со старым документом. Новый документ с той же линией забирает свой неистёкший lease сразу и не ждёт 60 секунд.
- Второй живой документ с той же линией lock не получает и писать не может.
- Неистёкший lease другой линии не подменяется. Конфликт выбрасывает `MockWriterHeldError` до изменения записи.

Тесты: `repository.test.ts` — reload с lease `+60s` пишет новым epoch; дубликат с той же линией получает `writeLocked`, update и reset бросают `MockWriterHeldError`, `ownerId` и `accessVersion` остаются. Чужой `tab-other-live` по-прежнему не вытесняется.

Браузер, origin 5178:

- Обычный reload вкладки конструктора сохранил линию `tab-7536f7b5-f895-4128-9065-aed878684167`. Оболочка с «Узел Б» была на месте примерно через 5 секунд. PATCH того же узла вернул 200, имя осталось «Узел Б». Это внутри окна 60 секунд, ответа `mock_writer_held` не было. Первый ручной PATCH смотрел не в то хранилище сессии и получил 401 `expired`; повтор с текущей авторизацией страницы дал 200.
- Команды «Дублировать вкладку» в инструменте браузера нет. Вторая вкладка открыта отдельно, и в неё до старта приложения записан тот же `inlog:mock:writer-tab`, который копирует дублирование. PATCH из второй вкладки вернул 409 `mock_writer_held`. Имя узла осталось «Узел Б». Первая вкладка после этого снова получила 200 на тот же PATCH.

### Переключение организации

Сообщение «A related id does not belong to this organization. Nothing was saved.» — это `invalid_relation` конструктора (`RELATION_DETAIL`), не сборка отчёта. Его даёт, в частности, GET `structure-element-field`, если `group` не принадлежит организации из URL. Рядом GET узла из чужой организации отвечает 404 без `detail`, и `errorsHandler` показывает `errors.server-error`.

Причина: `useGetAdminPanelNodesQuery` отдаёт в `data` список предыдущей организации, пока для новой ещё нет ответа, и при этом `isLoading` уже false. Страница выбирала прежний `node` и вместе с новым `organizationId` запрашивала узел и поля. Это не сохранение по кнопке, но запрос уходил сам.

Исправление: выбор узла и синхронизация URL смотрят только на `currentData` текущей организации. Пока этого списка нет, редактор не монтируется и чужой id не подставляется. Уже начатые обработчики держат организацию и узел, с которыми были вызваны. Успешный ответ не показывает toast, если на экране уже другая пара. Поздний отчёт строк кладётся под ключ исходной пары и не рисуется на новом экране. Ошибку запроса, который всё-таки относится к текущему экрану, код по-прежнему показывает.

Отдельно значение MultiSelect для связей сразу включает фиксированного родителя. Эффект самого MultiSelect больше не получает повод вызвать сохранение только из-за этого расхождения.
