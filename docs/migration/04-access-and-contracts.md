# Модель доступа и границы контрактов

Проектные предложения, не уже существующий backend. За основу взят исторический audit master c88fbde от 25 октября; актуальные DTO Cursor читает заново. Все новые endpoints помечаются proposed.

## Независимые понятия
1. Аутентификация — кто вошёл: локально или через корпоративную систему.
2. Provisioning — когда в inLog появляется/обновляется сотрудник: первый вход, предварительная синхронизация или ручное добавление.
3. Авторизация — что сотруднику разрешено. Успех SSO сам по себе не выдаёт рабочие или административные права.

## Доступ
User, Organization, Membership, Role, RoleAssignment, Grant и DelegationGrant — разные сущности. Role имеет ID и произвольное display name. Системное полномочие corporate_superadmin не выдаётся созданием одноимённой роли. Учитывать два типа организации: laboratory/customer; подразделения опциональны, не обязательный новый уровень.
Grant = ресурс + действие + scope (corporation, organization ID, project ID или свои записи там, где поддерживается). Resource может ссылаться на конкретную новую таблицу/раздел. Используем только нужные scopes, без произвольных сложных условий в первом этапе. Несколько ролей объединяют доступы в своих областях; отсутствие разрешения — запрет. Effective grants отдельно от delegation grants. Право создавать/редактировать роль и право назначать её отдельно. Проверка subset делегирования сравнивает действие/ресурс и область, а не только строковые названия permissions.
Legacy admin/member/editor/super_admin сохраняются как входной формат старых DTO и временная явная mapping table. Не делать org admin корпоративным администратором. Точный переход и guards существующих разделов — этап 2/4. На этапе 1 есть access model и проверяемые fixtures, но не полный редактор ролей и не обещание защиты всех старых экранов.

## Текущий login и proposed API
Существующий POST auth/login/ принимает email/password и возвращает access_token/refresh_token/user. GET users/me/ и POST auth/token/verify/ поддержать в моках текущими shapes. Текущая форма принимает почту: свободный логин не обещать без согласования. Existing logout/recovery/email flows сохраняются через adapters.
Предлагаемые новые ресурсы: authentication/capabilities; session/access; installation/status/initialize; roles/assignments; mock identity flow. Точные URL и DTO согласуются с Григорием, отмечаются current/proposed в docs. Не делать настоящие endpoint URL из картинки обязательными.
Capabilities показывают доступные методы входа, provider label и безопасный start URL/команду начала, но не secrets. Session payload содержит identity ID, доступные memberships, effective grants, delegation grants, accessVersion; источник истины проверяется сервером.
SSO identity связать по (issuer/providerId, externalSubject), не по совпадению email. Самостоятельная привязка по внешней почте не даёт полномочий. Mock profiles имеют фиксированные subject ID и provider mock-corporate.

## Ошибки и сессии
Неверные local credentials — ошибка формы без redirect. 401 защищённого запроса — один logout даже при нескольких ответах. 403 — недостаточно прав без выхода. Network/5xx — возможность повтора без очистки пользовательского черновика. Account blocked и employee without grants — разные состояния.
Logout: завершить session state, удалить только её access/refresh keys, reset всех восьми существующих API caches и новых пользовательских slices, остановить WS/подписки. Очистить незавершённые запросы/черновики, относящиеся к предыдущему пользователю, не показывать старый профиль в новом входе. Whiteboard и demo DB не стирать; персистентные сцены на следующем этапе показывать только допустимому owner/scope. Сохранность не означает доступ к чужой сцене.

## Первое назначение владельца — этап 3
Local: доверенный одноразовый код позволяет создать первого superadmin на backend. SSO: уполномоченный сотрудник проходит корпоративную проверку, а серверная процедура первоначальной настройки назначает ему полномочие. Любой первый вошедший сотрудник не становится владельцем. Не требовать отдельного локального пароля для SSO-пользователя. После назначения initial-owner операция закрыта атомарно. Прерванный мастер доступен уже назначенному владельцу. Восстановление/аварийный доступ согласуются отдельно с ИТ и ИБ, vendor account не создаётся автоматически.
