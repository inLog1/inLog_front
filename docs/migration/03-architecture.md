# Архитектура перехода

## FSD: используем существующие слои
Не нужно создавать проект заново. Новый код размещается в корректных слоях, старый двигается по мере реального изменения.

| Путь (предлагаемый) | Ответственность |
|---|---|
| app/bootstrap | Проверка режима, ожидание запуска MSW перед render |
| app/providers, app/routing, app/store | Сборка зависимостей, маршруты/guards, store |
| app/mocks | Композиция domain-handlers, browser worker, fixtures и mock DB; это тестовая инфраструктура, не новый FSD-слой |
| app/routing/compat | Временные переходы старых URL с сохранением query-параметров |
| pages/auth/login | Композиция страницы входа |
| pages/setup, pages/home | Первый запуск и новая главная, когда дойдёт соответствующий этап |
| widgets/auth-layout, sidebar, header | Существующие layout-блоки: обновлять адресно |
| features/auth | Существующая форма/действия login, восстановление и logout |
| features/assign-role и аналогичные | Переиспользуемые пользовательские действия; создавать по необходимости |
| entities/session | Состояния сессии, session bootstrap, orchestration-independent selectors |
| entities/access | Effective permissions, membership scopes, can() без импортов app/store |
| entities/workspace | Выбор организации/проекта и его валидация; не копия серверных сущностей |
| entities/organization, user, task | Существующие домены и API; сохраняются |
| entities/table-schema, form-schema, section | Схемы будущих конструкторов, постепенно |
| shared/api | Технические baseQuery и новый центральный API service, без знания ролей/таблиц |
| shared/ui, shared/config | Текущие shadcn-примитивы, режим приложения, общие env-настройки |

Slices одного слоя не импортируют друг друга напрямую. app композирует bootstrap сессии, пользователя, доступа и workspace; не создавайте entities/session → entities/user → entities/session. При необходимости payload сессии содержит самостоятельные минимальные типы; legacy DTO переводится отдельным адаптером на границе. Нельзя переносить все доменные типы в shared для обхода FSD.
Переиспользуемый Can-компонент может жить в entities/access/ui; route guard композируется в app/routing. Не надо помещать бизнес-права в shared.
Существующие нарушения (например, импорт app/store из entities и User из shared DTO) фиксируются в долге, не исправляются массово в шаге login.
Конструктор бизнес-процессов в будущем — features/pages соответствующего домена, не deprecated FSD-слой src/processes.

## Владение состоянием
- RTK Query: пользовательские серверные данные, организации, роли, permissions, схемы, записи, задачи.
- Redux slice: небольшой client session status и выбранный контекст там, где нужен всему приложению. Не дублировать весь query cache.
- Локальный state/react-hook-form: открытое окно, ввод, черновик редактора.
- URL: адресуемые выборы org/project/task, фильтры и выбранная вкладка по установленным правилам.
- Mock DB: изменяемый набор вымышленных тестовых данных, schemaVersion и отдельный namespace в IndexedDB; не реальные пароли и не производственные данные. Git-ветка не изолирует браузерное хранилище.

## Организация и проект
На первом шаге URL прежних экранов не менять. На шаге 2A выбрать единый источник адресуемого контекста и устранить двустороннее зеркалирование в OrgProjectSelector. URL-параметр сам по себе не даёт доступа: валидируется по memberships и доступным проектам. Project должен относиться к выбранной org. При смене org сбрасываются несовместимые project/task/node и незавершённые запросы; query-keys включают нужный org/project. «Все организации» — отдельный корпоративный read scope, а не org=0 для записи.
Не грузить проекты первой организации только ради открытия layout; у нового суперадмина организаций может ещё не быть.

## API и mocks
Сохранить старые authApi/userApi/taskApi/adminApi и их exports. Для нового согласованного API один service в shared/api и injectEndpoints в доменах; не объединять старые API в первом PR. Указать способ инвалидации между старым/новым API до появления общей сущности в обоих.
UI не знает, используется MSW или backend. Mock/live — явная env-конфигурация, проверяемая до запросов. В mock-mode использовать локальный base URL и блокировать необработанные запросы API (показать диагностическую ошибку), не пропускать их незаметно в production backend. Статические ресурсы и Vite HMR не блокировать.
Запуск MSW await до ReactDOM.render. При live-mode не импортировать/не запускать worker, не применять fake token; при смене режима перезапускать приложение и завершать его worker, если он был активен. Mock build для презентации — отдельная конфигурация, по умолчанию выпуск live без mock-доступа.
Первый шаг покрывает login/me/verify/logout и необходимые bootstrap-запросы. Полный mock старого конструктора и задач — этап 2A; отсутствие handlers сейчас не означает готовность этих экранов offline. В mock-mode отключать живой WebSocket. Никаких setTimeout-ответов или фикстур внутри React-компонентов.
Моки проверяют разрешения и связи данных для полезной демонстрации. Это не реальная граница безопасности: backend повторяет проверки самостоятельно.

## Сохранение старого конструктора
До расширения нужны fixtures узлов/вкладок/полей/строк/связей/отчётов и маршрутная регрессия. Таблица как физическая серверная структура не создаётся frontend-кодом. Новая модель схемы — метаданные, обсуждаемые с backend.
Adapter хранит source IDs и неподдержанные metadata; не выбрасывает старые свойства. Не считать узел старого дерева автоматически одной новой таблицей. Сначала описать соответствия на реальных fixtures. Миграция — отдельная версия, dry run, отчёт об ошибках, экспорт и обратимое применение; исходный формат доступен до подтверждения результата.
Новые поля получают стабильные ID, подписи отдельно, значения связаны с ID. Не дублировать записи ради другой формы или раздела.

## Что тестировать
Сложные правила: access scopes/delegation, bootstrap/401/403, переключение пользователей, совместимость adapter и schema versions, сохранение URL-context. Интеграционные тесты с MSW и важнейшие сценарии UI. Не писать тесты на каждую кнопку или стили. Ввести минимальный test setup только под текущие риски; не отключать strict/lint и не применять массовый --fix.


## Дополнение 26 октября: SSO и изоляция режимов
Две независимые настройки: apiMode=mock|live и authMode=local|sso|mixed. apiMode задаётся безопасной конфигурацией сборки/запуска (default live), auth capabilities могут приходить от установки. Dev-панель умеет менять authMode только внутри mock-набора. Нельзя произвольным браузерным переключателем превратить production в mock-доступ.
Сессия единая независимо от способа подтверждения личности. Mock SSO существует только в dev/test mock build; интерфейс перехода не отправляет корпоративный пароль в inLog. В live при отсутствии провайдера кнопка SSO скрыта/показано объяснение конфигурации, но не выполняется фиктивный успех.
Токены и данные mock/live используют разные namespaces и один технический session-storage adapter для всех потребителей: baseQuery, guards, WS, selectors, logout. Старые live-ключи не копировать автоматически в mock; описать совместимость текущего live. Demo data и session metadata имеют отдельные ключи. Переключение режима требует полной очистки текущей session/cache, остановки subscriptions/worker и перезапуска bootstrap. В live-сборке mock UI/handlers не импортируются и не регистрируются.
Выход удаляет сессию, но не persisted mock DB; «сброс тестовых данных» очищает только собственный namespace mock DB после подтверждения и завершает mock sessions. Сохранять любые внешние ключи/сцены. При наличии разных mock namespace обеспечить независимость тестом, не обещать изоляцию только из-за разных Git branches.
Для состояния «новая установка» хранить phase separately: uninitialized → owner-assigned → configuring → ready. Аккаунт владельца и «мастер полностью завершён» — разные факты. Фаза 1 только выбирает/сохраняет этот preset и показывает честное состояние; сам мастер — этап 3. Не притворяться, что preset уже проверяет реальную серверную bootstrap-защиту.
