# Моки и тестовые аккаунты

Цель: входить разными людьми через настоящий product login, меняя ответы API и данные, а не проверять CSS отдельными ветками roleName в компонентах.

## Настройки
apiMode mock/live отдельно от authMode local/sso/mixed. Разработка — отдельный именованный namespace, например inlog:mock:corporate-v2, schemaVersion=1. Live сессия хранится отдельно. На другой Git-ветке с тем же origin хранилище то же самое, пока namespace не изменён. Не записывать истинный backend URL как fallback в mock-конфигурации.

## Исходный набор ready
Корпорация «Демо-корпорация», лаборатория А (org 101), лаборатория Б (org 102), организация-заказчик (org 201). Проект 1001 относится к 101, проект 1002 — к 102. Все имена/ID вымышленные. Стабильные IDs сохраняются при reload.

| Аккаунт | Тестовая почта | Начальное назначение | Что ожидаем |
|---|---|---|---|
| Корпоративный superadmin | owner@example.test | Системное полномочие в этой demo corporation | Управление установкой и организациями; права не зависят от подписи роли |
| Админ лаборатории А | admin.a@example.test | Org 101, ограниченные management/delegation grants | Управление только разрешённым в А, без полномочий по Б |
| Сотрудник А | employee.a@example.test | Membership 101 и рабочие grants | Рабочие данные А, без управления ролями |
| Сотрудник Б | employee.b@example.test | Membership 102 | Отсутствие данных А, свой project 1002 |
| Заказчик | customer@example.test | Membership 201, работа со своими заявками | Без внутренних данных лабораторий |
| Без назначений | pending@example.test | Подтверждённая identity, рабочих grants нет | «Доступ пока не назначен», выход/помощь доступны |

Для этих вымышленных локальных mock-входов единый **публичный тестовый пароль `InlogDemo2026!`**. Он не используется в live и не является секретом. Тестовые пароли — только константы fixtures, не сохранять пользовательский ввод/пароли в DB/логах. У SSO-личностей есть независимые subject ID; одного email недостаточно для привязки.
Ни один из перечисленных аккаунтов не добавляется в настоящий backend. Отдельный dev control может пометить текущую demo identity blocked для негативной проверки; это состояние отличается от отсутствия grants.

## Изменяемое хранилище
В первый этап входят persisted mock DB/repository и seed для users, memberships, role/grant definitions/assignments, settings и simulated session metadata. Это основа, не готовый CRUD-интерфейс всех доменов. RTK Query получает данные через MSW; React-компоненты не читают IndexedDB напрямую.
Операции после logout/reload должны читать тот же DB, а не восстанавливать seed при каждом render. schemaVersion mismatch даёт управляемый upgrade/reset выбор только для mock DB, без молчаливого стирания. Минимальный test через repository/handler меняет тестовое назначение и проверяет его сохранение после нового login; production role editor будет на этапе 4.
Task/constructor entities добавляются в эту же основу на этапе 2: общая DB для списка, Kanban, Gantt и детализации, а не отдельные массивы на каждую страницу.

## Dev-панель — только mock build
Компактная сворачиваемая кнопка «Тестирование». Не часть обычного login и не список выбора роли для настоящего сотрудника.
- Выбор аккаунта с полным завершением прошлой сессии и новым bootstrap. Не просто перезаписать user в store.
- Auth mode local/sso/mixed: сохраняется внутри mock settings, смена завершает текущую сессию.
- Сценарии ready/uninitialized: подтверждение смены preset, создание нового набора только в mock namespace; завершаются текущие sessions. На этапе 1 uninitialized даёт понятное состояние «Требуется первичная настройка» без реализации мастера; screen design/setup — ориентир этапа 3.
- Ошибки: неверный пароль, blocked, expired session, 403 на тестовом ресурсе, network/5xx, отмена/ошибка SSO. Внедрение ошибки ограничено выбранным endpoint, не ломает все assets.
- «Сбросить тестовые данные»: подтверждение, reset только своего namespace и caches, возврат к login. Logout никогда не равен reset.
- Малозаметная подпись mock/dev; в live её и самого обходного входа нет.

## Два способа тестирования
Product login — почта/тестовый пароль. Mock SSO — кнопка → явно подписанная тестовая корпоративная страница → выбор вымышленной личности → подтверждение/отмена → общая сессия. Там не вводится корпоративный пароль.
Dev quick switch ускоряет работу, но не заменяет тесты login/SSO через обычный путь. Все три способа завершаются одинаковым bootstrap/effective-access.

## Ограничения
Первый этап подтверждает lifecycle auth и разделение fixtures. Полный запрет на любые операции старого конструктора/задач на всех уровнях пока не реализован: handlers/guards этих доменов — этап 2/4. Нельзя выдавать UI-моки за серверную безопасность. После подключения backend те же разрешённые/запрещённые сценарии повторяются на сервере.
