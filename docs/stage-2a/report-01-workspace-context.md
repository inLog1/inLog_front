# Отчёт подшага 2А-1

1. Версия: 27 октября 2026. Ветка `migration/stage-01-auth`, HEAD `9be407e` (`fix: add changes for non auth zone`). Изменения не закоммичены и не отправлены. Reset, clean и push не выполнялись. Секреты в отчёт не включены.

2. Что работает. Один механизм контекста: URL-параметры `org` и `project` — единственное сохранённое значение выбора. Хук `useEnsureOrgProjectParams` остаётся публичной точкой; чистый разбор вынесен в `workspace-context.ts`. Списки организаций и проектов приходят из существующих RTK Query hooks. Допустимость подтверждается ответом API и, в mock, эффективными grants.

   Состояния: `loading`, `ready`, `choose`, `empty`, `forbidden`, `not-found`, `error`. Автовыбор только если параметра нет и вариант ровно один (`history.replace`, чужой явный id не затирается). Несколько вариантов — экран выбора. Явный некорректный, неизвестный или чужой id остаётся в ссылке и показывает свой экран. Пустой список не маскируется под ошибку; ошибка загрузки даёт повтор.

   Организационные разделы (конструктор, отчёты) открываются без проекта. Проектные разделы не монтируют задачи, пока `projectId` не подтверждён. Смена организации сбрасывает `project`, `task`, `node`, `tab`. Смена проекта сбрасывает `task` и не переносит slug. Поздний список чужой организации не выбирает её проект: строки фильтруются по каноническому `organization`.

   Ограничение. В live ресурсные grants на клиенте не блокируют раздел: запрос сессии access пропускается, решение остаётся за backend. Mock outbound на реальный backend по-прежнему запрещён. CRUD организаций и проектов не делался. Handlers задач, конструктора и отчётов остаются 501 и не подменяются пустым успехом.

4. Права. `grantAllows` учитывает scope corporation / organization / project. Название роли и legacy `user.role` не выдают новый доступ. Администратор лаборатории не получает `corporate_superadmin` и не получает `tasks.read`.

   Предлагаемое расширение контракта, только в свежем seed, без тихой выдачи уже сохранённым пользователям:
   - `constructor.schema` `read` / `update` — конфигурация конструктора;
   - `constructor.records` `read` / `update` — данные узла;
   - `reports` `read` / `generate`.
   `generate` покрывает только `generate`. Действия не выводятся друг из друга. Проектный grant не открывает конструктор и отчёты организации и не открывает другой проект.

   Свежий seed: владелец получает `tasks.read` и перечисленные коды конструктора и отчётов, они же в его каталоге делегирования. Администратор лаборатории А получает коды конструктора и отчётов, без `tasks.read`; каталог делегирования остаётся `g-members-read`. Роль сотрудника по-прежнему только `g-tasks` и `g-projects`. Добавлены пользователь 7 `project.only@example.test` (проектный `projects.read` и `tasks.read` только на проект 1001) и проект 1003 «Проект А-2» в организации 101. Организация 201 по-прежнему без проектов.

   Положительно в mock: лаборатория А видит свои проекты и не видит Б; сотрудник изолирован; проектный пользователь видит только 1001; заказчик видит организацию 201 и пустой список проектов; чужая организация 403 без имени; неизвестный id 404; проект другой организации у того, кто может его прочитать, даёт mismatch и канонический `organization`, а не клиентский id.

   Отрицательно: membership сам по себе организацию не открывает; `requests.read` не перечисляет проекты; отзыв назначений и делегирования переводит пользователя в pending, списки отвечают 403.

5. Хранение. Два ограничения из отчёта 2А-0 в текущих исходниках закрыты и этим подшагом не переоткрывались. `resetMockNamespace` заменяет запись `root` в одной транзакции и не вызывает `indexedDB.deleteDatabase` — это проверяет `repository.test.ts`. Миграция отсутствующего `delegationGrantIds` пишет `[]` и не копирует каталог сида и новые grants. Версия документа `MOCK_SCHEMA_VERSION` 2, версия IndexedDB 1, namespace `inlog:mock:corporate-v2`. Более новый неизвестный документ не стирается.

   База не сбрасывалась и namespace не менялся. Уже сохранённый снимок не получает пользователя 7, проект 1003 и новые коды конструктора и отчётов, пока его явно не пересоздадут. Тест миграции фиксирует владельца с `grantIds: ['g-projects']` без `delegationGrantIds`: после открытия список остаётся прежним и `g-constructor-schema-read` не появляется.

   В браузере IDE база оказалась свежим seed (в панели виден Белов и «Проект А-2»). Это не снимок пользователя из прошлого подшага. Кнопка сброса не нажималась. Другая вкладка держала writer: `POST /mock-api/auth/dev/settings/` вернул 409 `mock_writer_held`, поэтому fault и блок из этой вкладки не записывались.

8. Непокрытые endpoints. Задачи, шаблоны, статусы, канбан, дорожная карта, узлы конструктора, группы, генерация отчёта и CRUD организаций/проектов по-прежнему 501 `mock_coverage_gap`. 9. Backend. Существующий контракт списков и карточек сохранён. Карточка проекта должна отдавать каноническую организацию; клиентский `organizationId` рядом с `projectId` не является источником принадлежности. 404 — объект неизвестен или не этой корпорации. 403 — объект этой корпорации есть, доступа нет, тело `{ code: 'forbidden' }` без имени. Видимость организации не равна списку всех её проектов. Проектный grant перечисляет только этот проект.

   Предлагаемое расширение: ресурсные коды из пункта 4. Их нужно проверять на сервере. Клиент в mock только не монтирует раздел. Сохранённым пользователям новые коды сами не выдаются.

10. Готовность к 2А-2. Контекст организации и проекта для задач, конструктора и отчётов есть: разделы получают проверенный id и не стартуют запрос до готовности. Подшаг 2А-2 не начинался. Блокер следующего подшага — handlers задач всё ещё 501; пустым успехом их заменять нельзя.
