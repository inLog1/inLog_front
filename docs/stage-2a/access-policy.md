# Политика доступа для реализации

Обычная роль — именованный набор разрешений. Название произвольное, логика не сравнивает строки «Администратор»/«Суперадмин». Назначение связывает пользователя, роль и область действия. Системная capability корпоративного суперадмина — отдельный механизм в одной корпоративной установке.

Операционное право означает «могу сделать». Полномочие делегирования означает «могу выдать вот этот набор в этой области». Для назначения роли нужны доступ к управлению назначениями, делегирование каждого разрешения целевой роли и корректность области. Одного assignments.update недостаточно. Дальнейшее делегирование запрещено без отдельного разрешения. После изменения роли все связанные назначения перепроверяются: редактирование роли не должно обходить ограничения назначения.

Глобальные шаблоны ролей и локальные роли не должны изменяться за пределами разрешённой области. На этом шаге полный редактор не создаётся, но mutation/service проверяет те же инварианты.

Все запросы проходят: действительная сессия → активный пользователь → существующий ресурс → каноническая принадлежность → операционное право → операция. Ответ не раскрывает чужие данные. Вариант 403 или маскирующий 404 для чужого ID выбирается единообразно и фиксируется; неизвестный mock endpoint остаётся 501.

## Предлагаемое расширение каталога, ещё не production API

| Ресурс | Действия | Область |
|---|---|---|
| tasks | read/create/update/delete; отдельное назначение при необходимости | project или organization с проверенной принадлежностью |
| constructor.schema | read/create/update/delete | organization |
| constructor.records | read/create/update/delete | organization, связь со схемой проверяется |
| reports | read/generate | organization |
| assignments | read/update | область назначения + делегирование выдаваемого набора |
| notifications | read/update/delete | собственные объекты |

Это предложения для согласования с backend; не переименовывать существующие grants автоматически. Явно описать соответствие legacy операциям. manage/read/update/create не подразумевают друг друга без утверждённой таблицы. Не вводить wildcard на основе отображаемой роли.

В фикстурах owner получает явные полномочия установки, admin A — разрешённые операции своей лаборатории и ограниченное делегирование, employee A/B — свои проектные операции, customer — заявки, pending — ничего. Для отрицательных тестов нужны отдельные операционные/делегирующие назначения и запрещённые действия. Условия own проверяют автора/получателя самого объекта, а не userId из пользовательского запроса.

Заказчику не следует навсегда запрещать любые будущие данные конструкторов: позднее заявки будут формами на этом движке. Здесь закрываются лабораторные схемы и записи; пользовательская форма заявки получит отдельные права и опубликованное представление на будущем шаге.
