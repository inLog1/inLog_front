2. Что работает.

- `can` смотрит только операционные назначения. `canDelegate` — отдельная проверка каталога делегирования роли и явно переданных записей. Запись `members.read` у сотрудника А больше не даёт ему обычное чтение состава.
- Администратор лаборатории А может назначить роль, в которой только `members.read`, сотруднику своей лаборатории. Назначить `role-owner`, выдать дальнейшее делегирование или поднять собственные права этой ролью нельзя.
- `projectId`, `organizationId` и `corporationId` сверяются с реестром. Подмена организации у проекта 1002 и неизвестные id отвергаются.
- Назначение на область `corporation` требует отдельную capability `corporate_superadmin` этой единственной установки. Название роли capability не даёт. `can` из-за capability не становится истинным для произвольного ресурса.
- Уже вошедший заблокированный субъект получает 403 на тестовый ресурс, организации и проекты. `session/access` остаётся 200 с `accessState: blocked` и пустыми списками. `users/me` и `token/verify` для экрана блокировки сохраняются. Pending не получает списки организаций и проектов.
- Локальный выход снимает токен, кэши и рабочую область до ответа `auth/logout/`. Удалённый выход идёт со снимком старого токена и не стирает сессию, записанную пока запрос ещё шёл. Поздний login/SSO не записывает токен после инвалидации билета. Ответ API с тем же `null`-токеном, но новой generation сессии, в кэш не попадает.
- Подписки `initiate` в bootstrap снимаются при завершении и при повторном запуске эффекта.
- Новый ключ доски включает режим и namespace. Прежние ключи не читаются, не удаляются и не копируются. Смена субъекта или режима меняет ключ холста.
- В mock запрос на известный live origin и на посторонний абсолютный API URL получает 501 `mock_upstream_blocked` без сетевого вызова. Модули приложения, asset destination и websocket HMR пропускаются.
- `deleteDatabase` при `onblocked` больше не считается успехом: reset отвечает 409 `reset_blocked`.

4. Права.

Таблица действий явная и не выводит одно действие из другого: `read`, `create`, `update`, `delete`, `manage`, `assign`, `delegate` покрывают только себя. `manage` не включает `read` или `delete`, `create` и `update` не включают `read`.

Операционные права приходят из `grantIds` роли и области назначения. Делегируемые права — из `delegationGrantIds` роли и из записи делегирования, если у отправителя этот набор есть в каталоге делегирования. Полученная запись не даёт права передать делегирование дальше: для непустого `delegationGrantIds` нужно отдельное `delegations.delegate`.

В сиде владелец имеет операционные права установки и отдельный каталог делегирования, включая `delegations.delegate`. Администратор А имеет операции лаборатории 101 и может делегировать только `members.read`. Сотрудники имеют проектные `tasks.read` и `projects.read`. Заказчик имеет `requests.read` и `requests.create`. Pending не имеет назначений. Capability `corporate_superadmin` записана только у владельца.

Положительно: сотрудник А до назначения не читает `members`, но `canDelegate` для `members.read` в организации 101 истинен; после назначения `role-members-reader` чтение становится истинным. Владелец может добавить `test-resource.read` роли сотрудника, и оба проектных назначения получают это право. Организация 101 покрывает проект 1001. Активный сотрудник А получает «Лаборатория А» и не получает «Лаборатория Б».

Отрицательно: `members.manage` не покрывает `members.read`; проект 1002 с подставленной организацией 101 и неизвестный проект отвергаются; администратор не назначает `role-owner` ни себе, ни сотруднику, состояние не меняется; самоназначение `members.read` даёт 403 `self_elevation`; роль с дальнейшим делегированием администратору недоступна; правка роли сотрудника с `test-resource.read` администратором не меняет роль; скопированная роль владельца без capability не меняет корпоративное назначение; `can` владельца для `tasks.delete` ложно.

5. Хранение.

IndexedDB остаётся `inlog:mock:corporate-v2`, запись `root`, `schemaVersion` 1. Поле `delegationGrantIds` необязательное: в старом снимке его отсутствие означает, что роль ничего не делегирует. Назначения, пользователи и настройки не переписываются и база при загрузке не засевается заново. Автоматически дописывать каталог делегирования в уже изменённую роль нельзя: это расширило бы права. Свежий сид и явный reset получают новый каталог.

Очередь репозитория сериализует операции только внутри одной JS-среды. Она не блокирует вторую вкладку и не является межвкладочной транзакцией. `onblocked` — ошибка `ResetBlockedError`, HTTP 409. Пока блокирующее соединение открыто, прежняя запись читается. Если другая вкладка позже закроется, браузер может довести уже начатый `deleteDatabase` до конца: отменить его нельзя. Следующее открытие пустой базы создаст новый сид. Успехом такой сброс не объявляется.

Ключ доски v2: `inlog-whiteboard:v2:${mode}:${namespace}:${storageKey}:u${subjectId}`. Namespace mock — `inlog:mock:corporate-v2`, live — `live`. Старые ключи без `v2` остаются. Загрузчик их не открывает. Восстановление — отдельное явное действие со списком старых ключей; экрана восстановления нет.

Logout не вызывает `localStorage.clear()` и не сбрасывает mock-базу. Тема в браузерной проверке осталась.

9. Что передать backend.

Существующие контракты login, verify, logout, `users/me`, организации и проекты сохраняют прежние формы. Сервер должен сам повторять проверки, а не полагаться на скрытые кнопки.

Proposed, не production API: `session/access`, `mock/test-assignments`, `auth/dev/*`. Для blocked/pending `session/access` отдаёт состояние экрана и пустые списки. Назначение роли требует право управлять назначениями в канонической области и делегирование каждого права целевой роли. Дальнейшее делегирование — отдельное право `delegations.delegate`. Действия не подразумевают друг друга. `corporate_superadmin` — отдельная capability одной установки, не wildcard и не следствие названия роли. Чужой или противоречивый `project/organization/corporation` — отказ. 403 не очищает сессию. Неизвестный mock-путь остаётся 501.

Спорное решение: область `corporation` у назначения требует capability, а не только `assignments.update` с роли. Организационная область по-прежнему проверяется операционным `assignments.update`.

10. Готовность к 2А-1.

Критерии 2А-0 выполнены: четыре review-теста зелёные, разрешённое делегирование тоже проходит, блокировка с живым токеном запрещает данные, поздние login/logout не меняют следующую сессию, mock и live не читают одну сцену, reset при `onblocked` не сообщает успех. Исходные тесты пароля, SSO, pending и namespace остаются зелёными. Lint-долг не вырос.

Блокеров для чтения промпта 2А-1 нет. Сам подшаг 1, новая главная, визуальная перестройка sidebar и редактор ролей не начинались. Перед 2А-1 стоит помнить: старая mock-база без `delegationGrantIds` не получает каталог делегирования молча; для фикстур нужен явный reset своего namespace.
