# Пользователи и назначения

Справочник пользователей не заменяет роли, назначения и membership. Это отдельное чтение поверх уже существующих `AccessRole`, `RoleAssignment`, `AccessScope` и capability `corporate_superadmin`.

## Что разделено

| Действие | Чем разрешено |
| --- | --- |
| Читать справочник пользователей | `access-users.read` в области либо capability установки |
| Назначить или снять роль | прежние `createAssignment` / `revokeAssignment`: `assignments.update`, делегируемый набор, область роли, получатель |
| Создать или изменить определение роли | прежние права роли, не чтение справочника |
| Передать делегирование | прежний набор `delegationGrantIds` |

`access-users.read` добавлен в каталог известных возможностей (`g-access-users-read`). Суперадминистратор получает его через capability и каталог, а не через сохранённую роль. В уже сохранённые обычные роли право само не дописывается. Выдать его можно в редакторе роли.

Право видеть пользователей или роли не даёт менять назначения. Операционные права не заменяют делегирование.

## Кого видно

Суперадминистратор установки видит всех пользователей своей корпорации, включая людей без membership и без назначений. Фильтр организации оставляет человека, если он состоит в этой организации или имеет видимое назначение в ней. «Все организации» — параметр обзора, а не область назначения. Организационное назначение остаётся организационным.

Обычный администратор видит только людей из организаций, где у него есть `access-users.read`: участников этих организаций и людей с видимым назначением там. Скрытый человек на чтении карточки отвечает `404 not_found`, как отсутствующий. Недоступная организация в фильтре отвечает `403 forbidden` без count. Поиск и count считаются только по видимому набору.

Назначения в строке — только те, чью область актор может читать. У суперадминистратора покрытие `corporation`. У остальных покрытие `granted`, и подпись списка — «Назначения в доступной области». Отсутствие назначений в чужих областях не подписывается как «Ролей нет» и не помечается скрытым счётчиком.

## Назначение и снятие

Активный выбор роли содержит только пары «область + роль», которые проходят ту же проверку, что запись: актор управляет владельцем роли и целевой областью, владелец роли покрывает область, получатель допустим, набор роли делегируется, самоповышение обычного администратора запрещено. Видимая, но недоступная роль показывается с причиной.

`canRevoke` равен `canManageAssignment` для области этого назначения. Прямой `DELETE` проходит ту же проверку. Снимается один `assignmentId`. Определение роли и membership не удаляются. Снятие последней роли не убирает принадлежность организации.

Отдельной атомарной замены нет. Безопасное изменение — явно добавить назначение и явно снять прежнее. Отказ второго запроса не снимает уже созданное.

Точный повтор `userId + roleId + scope` остаётся идемпотентным и не создаёт дубль.

## Capability

`corporate_superadmin` читается только из `systemCapabilities`. Название роли, `roleId` и тело обычного назначения её не выдают и не снимают. В карточке такого человека есть бейдж «Суперадминистратор корпорации». Управление capability в этот этап не входит. Capability по-прежнему покрывает известный каталог собственной корпорации и не обходит блокировку, ревизию и writer lock.

## Версия доступа

Изменяющие запросы карточки передают `expectedAccessVersion` из прочитанной карточки. Устаревшая версия — `409 stale_write`, данные не меняются, запрос не повторяется сам. После успешной записи инвалидируются `AccessControl`, `SessionAccess` и кэши организаций, проектов, задач, конструктора, форм, табличных представлений и разделов. Другая вкладка узнаёт новую версию при следующем чтении `session/access` (период около 20 секунд). Отдельного кэша полномочий нет.

Список и карточка рисуются из `currentData`, если эхо запроса совпадает с текущим контекстом. Смена пользователя сбрасывает диалог за счёт нового экземпляра страницы.
