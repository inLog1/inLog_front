# 2А-1 — единый контекст организации и проекта

Начинать после принятого отчёта 2А-0. Прочитай docs/stage-2a/workspace-context.md и существующий useEnsureOrgProjectParams.ts, org-project-selector, AppRouter, routes, organizationApi/projectApi и потребителей URL.

Развивай существующий механизм выбора, сохраняя совместимость внешнего интерфейса там, где возможно. URL хранит текущий выбор; доступность определяется актуальными membership/grants и канонической принадлежностью проекта. Не поддерживай независимо тот же выбор в localStorage, Redux и локальном state. Временное UI состояние допускается, но не второй авторитетный контекст.

Реализуй состояния loading/ready/empty/forbidden/not-found/error и выбор при отсутствии параметров. Ошибочный/чужой явный URL не подменяй первой организацией. Пока контекст не проверен, зависимые запросы пропускаются. Переключение организации сбрасывает проект и несовместимые параметры задачи/узла/вкладки и выделение; старые данные не мелькают. Back/forward и refresh работают. returnTo сохраняет безопасный относительный путь с параметрами.

Расширь существующие mock org/project handlers для корректной выдачи доступных объектов, включая project-scoped grants. Доступ к карточке своей организации не равен чтению всех её проектов. Здесь CRUD организаций и проектов не нужен.

Введи минимальные guards и обработку отказов для constructor/reports/tasks; не переноси всю legacy админку на новый RBAC и не выдавай администратору лаборатории corporate privilege. Если ресурсные коды отсутствуют — добавь явные предложения в каталог permissions и фикстуры, согласуй их в документации. Новая главная и новый дизайн sidebar не входят в подшаг.

Готово: две лаборатории не видят данные друг друга; клиент не получает задачи и конфигурацию конструктора; пользователь без назначений видит понятный экран; отсутствие проекта не ломает разделы уровня организации. Добавь тест URL, подставленного scope, переключения во время запроса и ошибок metadata.

Общие условия: React + Tailwind + shadcn + RTK Query + FSD сохраняются. Не переносить все папки, не переписывать задачи/конструктор, не менять production DTO ради удобства моков. Новые proposed endpoints отметить как mock-only. UI получает данные через RTK Query, а не импортирует сиды и handlers. Композиция приложения и запуск MSW — app; доменные типы и API — entities; пользовательские действия — features; shared не импортирует app. Не создавать универсальный движок до появления потребности. Минимальные точечные исправления старого кода допустимы с объяснением и проверкой регрессий.

Моки не обращаются к реальному API. Неизвестный mock endpoint отвечает 501 mock_coverage_gap. 401, 403, 404, сеть и 5xx различаются. Отказ доступа не очищает сессию как истёкший токен. Все новые ограничения выполняются в mock handler/service, а не только скрывают кнопку. В будущем backend должен реализовать те же проверки самостоятельно.

В конце: npm test, npm run build, lint с сравнением исходного долга и проверкой изменённых файлов; ручные сценарии текущего подшага. Не выдавать непроверенное за проверенное. Заполнить docs/stage-2a/report-template.md отдельным отчётом, указать оставшиеся ограничения и изменённые файлы. Следующий подшаг автоматически не начинать.
