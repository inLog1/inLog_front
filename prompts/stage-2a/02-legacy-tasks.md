# 2А-2 — существующие задачи на устойчивых моках

После 2А-1 прочитай текущие taskSlice/types/DTO, все потребители запросов задач, members/status/tag, scheduler, Kanban/Gantt и docs/stage-2a/legacy-api-map.md. Составь точный список вызовов. Моки должны обслужить существующий UI, не подменять его упрощённой новой страницей.

Разнеси auth/dev и tasks handlers по доменам; общий authenticated-principal и persistence вынеси без копирования логики. Сохрани экспорт hooks/аргументы/DTO taskApi. Реализуй list/detail/create/update/delete, подзадачи, назначение/снятие исполнителя и руководителя, комментарии, теги, статусы, файлы и минимальный список участников, требуемый экраном. Методы и payload читать из исходников. Не добавляй успешные заглушки для неработающих функций.

Сиды A/B должны различаться, но иметь по задаче с одинаковым slug для проверки изоляции. Все изменения сохраняются в IndexedDB и переживают reload. Блокировка, permission и принадлежность задачи проекту проверяются на каждой операции. Групповые изменения валидируй атомарно либо явно документируй поэлементный результат; не делай частичный успех молча.

Фильтры, поиск, сортировка и пагинация: семантика из текущих параметров; count относится к отфильтрованной выборке до пагинации. Проверь transformResponse taskType: нельзя фильтровать только одну страницу и выдавать её длину за общее число. Если нужна точечная коррекция клиента, сохрани внешний контракт и проверь live-совместимость; не обещай поведение сервера, которого нет.

Оптимистические updateTask ограничь projectId и идентичностью задачи. Учитывай удаление из фильтра/изменение сортировки; обеспечь rollback при отказе. Kanban, список, карточка и Gantt согласованы после изменения и возврата на экран. Для FormData не задавай вручную multipart Content-Type. Файлы — только локальные тестовые Blob, хранение/URL по persistence.md, без реальной загрузки наружу.

Готово: создать задачу и подзадачу, изменить статус/срок/участников/комментарий, приложить и удалить файл, обновить страницу, сменить проект и пользователя. Проверить отсутствие изменений у задачи с тем же slug в B и откат при 403/500. Существующие шаблоны/roadmap/statuses не удалять; непокрытое явно перечислить, не объявлять готовым весь scheduler.

Общие условия: React + Tailwind + shadcn + RTK Query + FSD сохраняются. Не переносить все папки, не переписывать задачи/конструктор, не менять production DTO ради удобства моков. Новые proposed endpoints отметить как mock-only. UI получает данные через RTK Query, а не импортирует сиды и handlers. Композиция приложения и запуск MSW — app; доменные типы и API — entities; пользовательские действия — features; shared не импортирует app. Не создавать универсальный движок до появления потребности. Минимальные точечные исправления старого кода допустимы с объяснением и проверкой регрессий.

Моки не обращаются к реальному API. Неизвестный mock endpoint отвечает 501 mock_coverage_gap. 401, 403, 404, сеть и 5xx различаются. Отказ доступа не очищает сессию как истёкший токен. Все новые ограничения выполняются в mock handler/service, а не только скрывают кнопку. В будущем backend должен реализовать те же проверки самостоятельно.

В конце: npm test, npm run build, lint с сравнением исходного долга и проверкой изменённых файлов; ручные сценарии текущего подшага. Не выдавать непроверенное за проверенное. Заполнить docs/stage-2a/report-template.md отдельным отчётом, указать оставшиеся ограничения и изменённые файлы. Следующий подшаг автоматически не начинать.
