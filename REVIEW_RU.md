# Проверка присланного проекта

Источник — локальный архив inlog_pack.7z. Проверка проведена по исходникам и CLI. Браузерные сценарии из отчёта пользователя повторно не выполнялись; реальный сервер не проверялся. Репозиторий пользователя не изменялся; для проверки использовалась распакованная копия.

## Что подтвердилось

`npm ci --ignore-scripts --no-audit --no-fund` завершился успешно. Исходные `npm test`: 6 файлов, 17 тестов, все проходят. `npm run build`: exit 0. Предупреждение о большом chunk остаётся. `npm run lint`: 150 замечаний, 123 ошибки и 27 предупреждений — совпадает с отчётом. Это исходный долг, его нельзя объявлять исправленным или скрывать отключением правил.

В коде есть раздельные ключи mock/live, session bootstrap, generation для защиты от устаревшей загрузки, проверка смены токена в baseQuery, IndexedDB и отдельная системная capability корпоративного суперадмина. Существующие модули задач и конструктора сохранены. Это рабочая основа для продолжения, но модель прав пока требует исправлений.

## Четыре воспроизведённых расхождения

Дополнительный файл review/review-boundaries.test.ts выполнен отдельно от исходных 17 тестов. Все четыре проверки ожидаемой границы сейчас падают. Это дефекты логики моков/клиента; из этого нельзя делать вывод о безопасности реального backend.

| Проверка | Сейчас | Ожидается |
|---|---|---|
| Пользователь 3 с правом делегирования members.read получает обычный доступ members.read | true | false: делегирование и выполнение разделены |
| project 1002 из организации 102 проверяется с подставленной organizationId 101 | true | false: сверка с реестром проектов |
| Администратор А заменяет своё назначение asg-admin на role-owner | 200 | 403: полный набор прав роли не разрешён к делегированию |
| Уже вошедший администратор после блокировки читает закрытый ресурс | 200 | 403 |

Третья проверка НЕ означает получение системной capability corporate_superadmin: она хранится отдельно. Ошибка — выдача более широких разрешений роли в области назначения без проверки полномочий на их выдачу.

Основные места: entities/access/model/grants.ts; app/mocks/auth/flow.ts. Текущий ACTION_COVERS неявно добавляет read к create/update, а manage не включает delete. Нужна явная согласованная таблица действий, а не догадки по названиям.

## Наблюдения по коду, требующие отдельных проверок

- perform-logout.ts сбрасывает кэш до ожидания logout-запроса, но очищает токен и закрывает UI после ожидания до 3 секунд. Проверить поздние запросы/повторное наполнение кэша и смену пользователя; локальное завершение должно быть немедленным.
- authSlice.ts записывает результат login без собственного билета попытки. Сравнение токенов в baseQuery не покрывает случай null → logout → null. Проверить поздний ответ login/SSO после выхода.
- SessionProvider использует initiate; проверить освобождение подписок на повторном bootstrap и StrictMode.
- Доска отделена по subjectId, но ключ не включает mock/live. Одинаковые ID и storageKey способны пересечься между режимами. Старые данные не удалять и не присваивать автоматически текущему пользователю.
- За пределами /mock-api/ handlers допускают passthrough. Проверить, что случайный абсолютный API URL в mock не уходит на реальный backend; статические файлы и HMR должны продолжать работать.
- IndexedDB reset считает onblocked успешным исходом. Нельзя сообщать об успешном сбросе, если другая вкладка блокирует удаление. Очередь в одном JS-контексте не обеспечивает сериализацию между вкладками.
- Оптимистическое обновление задачи проходит по спискам в кэше и сопоставляет slug без ограничения projectId. Проверить два проекта с одинаковым slug; исправлять точечно.
- В задаче при отправке FormData вручную задан multipart Content-Type. Проверить и убрать ручной заголовок, чтобы браузер сформировал boundary.

Это статические наблюдения, не дополнительные воспроизведённые падения. В подшаге 00 нужны проверки прежде, чем объявлять их закрытыми.

## Уточнения к отчёту этапа 1

В присланном AppRouter маршруты /admin/constructor и /admin/reports находятся вне legacy AdminRoute, хотя закрыты общей сессией. Нельзя считать их защищёнными правами администратора. Остальная старая админка использует user.role. При переходе на grants проверять каждый маршрут отдельно.

Уже существует features/org-project-selector/model/useEnsureOrgProjectParams.ts. Нужна эволюция этого механизма; второй независимый источник контекста создаст гонки. Сейчас невалидные ID могут заменяться первыми доступными, а ошибки запросов выглядеть пустыми списками.

Архив не содержит истории git: не подтверждены commit, отсутствие изменений других веток и статус push. Прототипы и требования лабораторий в этой проверке отдельно не сопоставлялись. Полноту продукта по ним этот пакет не подтверждает.
